# Глубокая перепись смыслового поля: инструкция

## Зачем это нужно

Глубокая перепись (`deep semantic census`) строит максимально полный, но открытый и
версионируемый эталон смыслов одного текста. Это **не утверждение, что смысл конечен**.
Это зафиксированное поле смысловых единиц при заданном источнике, контексте и политике
вывода.

Такой эталон позволяет раздельно проверить:

1. **ёмкость представления** — может ли FVSC/UMR/DRS записать единицу без потери;
2. **качество извлечения** — может ли парсер найти её в исходном тексте;
3. **вычислительную полезность** — можно ли затем правильно отвечать на запросы;
4. **безопасность** — не создаёт ли система лишних фактов, авторства или уверенности.

## Кто что делает

Codex может самостоятельно выполнить первичную разметку, привязку к источнику,
формализацию, поиск противоречий и несколько проходов насыщения. Такая разметка имеет
статус `candidate`.

Владелец текста нужен только там, где внешнего наблюдения недостаточно:

- личное намерение или переживание;
- значение авторского термина;
- допустимость метафорического прочтения;
- выбор между несколькими поддерживаемыми интерпретациями;
- решение, что утверждение действительно принадлежит владельцу.

До owner-review кандидат не становится owner-gold. Исправление одного пункта не требует
переписывать весь документ: решения записываются по идентификаторам смысловых единиц.

## Быстрый старт

1. Выберите один смыслонасыщенный текст: сначала достаточно 1–5 абзацев. Используйте
   собственный или разрешённый материал.
2. Скопируйте шаблон в приватную, игнорируемую Git папку:

   ```powershell
   New-Item -ItemType Directory -Force private_eval/deep_census
   Copy-Item docs/evaluation/DEEP_SEMANTIC_CENSUS_TEMPLATE_RU.md `
     private_eval/deep_census/census-001.md
   ```

3. Заполните только раздел `0. Передача текста`: вставьте текст или укажите точный
   локальный источник. При желании добавьте первое свободное понимание текста.
4. Передайте файл Codex. Codex заполнит кандидатную разметку и вернёт короткий список
   пунктов, где действительно требуется ваше решение.
5. Отметьте решения `confirmed`, `rejected` или `open`. Всё остальное можно оставить
   системе.

`private_eval/` игнорируется Git по умолчанию. Не добавляйте сырой личный текст в
`docs/`, `data/fixtures/` или коммит.

## Границы переписи

Перед разметкой фиксируются:

- точная ревизия текста;
- разрешённый контекст: только текст, соседние сообщения, биографический контекст и т. п.;
- разрешённое внешнее знание;
- максимальная глубина логических выводов;
- вопрос, ради которого смысл может быть вычислен.

Без этих границ цепочка выводов бесконечна: `собака -> животное -> живое -> объект ...`.
По умолчанию census включает содержание текста, непосредственные логические следствия,
пресуппозиции и явно отмеченные интерпретации, но не транзитивное замыкание всей мировой
энциклопедии.

## Статусы смысловых единиц

| Статус | Значение |
|---|---|
| `explicit` | выражено непосредственно, с учётом области отрицания и модальности |
| `entailed` | необходимо следует из текста и разрешённого контекста |
| `presupposed` | подано как уже предполагаемое или существующее |
| `defeasible` | правдоподобный, но отменяемый вывод |
| `interpretive` | допустимое более глубокое прочтение |
| `underdetermined` | источник не позволяет выбрать ответ |
| `rejected` | чтение проверено и отвергнуто владельцем либо противоречит источнику |

`explicit` не означает «факт действительности». Например, «возможно, он придёт» явно
выражает возможность прихода, но не утверждает сам приход.

## Решения владельца

| Решение | Значение |
|---|---|
| `not_reviewed` | кандидат ещё не проверен владельцем |
| `confirmed` | владелец подтверждает формулировку/прочтение |
| `rejected` | владелец отвергает его |
| `open` | владелец сознательно оставляет несколько вариантов |
| `not_applicable` | внешняя проверяемая единица, owner-review не нужен |

Низкая уверенность модели и решение владельца — разные поля. Модель может быть уверена в
своём чтении, которое владелец отклонит.

## Проходы разметки

### Проход 1 — целое

Записывается ядро текста, напряжение, цель высказывания и самое важное из того, чего текст
**не позволяет** утверждать. Этот проход делается до формальных схем.

### Проход 2 — опоры и участники

Создаются точные anchors, сущности, события, состояния, времена и голоса. Цитата,
пересказ, слова собеседника, лирический субъект и владелец не сливаются.

### Проход 3 — смысловые единицы

Каждая единица получает стабильный ID (`M001`), нормализованную формулировку, статус,
опоры, источник голоса, полярность, модальность, время, уверенность и owner-decision.
Формулировка сначала остаётся на естественном языке — UMR или DRS не должны заранее
ограничивать поле.

### Проход 4 — отношения и альтернативы

Отдельно фиксируются причинность, время, кореференция, часть/целое, условие, противоречие,
авторство и группы конкурирующих прочтений. Несовместимые варианты не усредняются.

### Проход 5 — границы и запросы

Добавляются привлекательные, но неподдержанные утверждения и вопросы, на которые
представление должно ответить либо корректно воздержаться.

### Проход 6 — насыщение

Текст перечитывается через разные линзы: буквальную, логическую, дискурсивную,
прагматическую, метафорическую, временную и owner-specific. Для каждого раунда считается
число новых принятых единиц и новых категорий.

Практический остановочный критерий: два последовательных прохода не добавляют новой
семантической категории и дают менее 5% новых содержательных единиц. Это не доказывает
абсолютную полноту, но делает степень насыщения наблюдаемой.

## Что считается готовым reference-census

- источник и его ревизия однозначны;
- каждая подтверждаемая единица имеет source anchor либо явно названа интерпретативной;
- голос/авторство не оставлены неявными;
- модальность и отрицание не превращены в утверждение факта;
- альтернативы и неподтверждаемые чтения записаны;
- owner-sensitive кандидаты прошли review или остались честно `open`;
- журнал насыщения показывает, где и почему остановилась разметка;
- черновик заморожен новой версией, а не переписан задним числом.

## Как затем сравниваются архитектуры

Для каждой `M*`/`R*` единицы отдельно отмечается:

- `native` — выражается структурно и непосредственно;
- `composed` — выражается композицией нескольких объектов;
- `opaque` — хранится лишь свободным текстом, вычисления не определены;
- `collapsed` — сливается с другой различимой единицей;
- `forced` — схема вынуждает добавить неподтверждённый элемент;
- `lost` — представить единицу нельзя.

Сначала выполняется ручное кодирование, измеряющее ёмкость. Автоматический парсер
проверяется отдельным прогоном. Итог публикуется как профиль по категориям, а не один
средний балл.
